## §1. The onset join gap — MECHANISM, PRE-DECLARED, AND ALREADY MEASURED

### §1.1 What was observed (072-01)
On the Lyra smoke, an anomaly entry carries `mask_value: 0` while that frame's mask PNG carries the
event's real tag, on **the first labelled frame of all four `FireWindow` events and neither
`ActorHidden` event (4/4 vs 0/2)**.

### §1.2 The mechanism I claim, and it is NOT the class split
**`FMulticastDelegateBase::Broadcast` calls bound functions in REVERSE registration order** —
`MulticastDelegateBase.h:163`, and the engine says so in its own comment:
`// call bound functions in reverse order, so we ignore any instances that may be added by callees`.

`UAnomalyCaptureSubsystem::Initialize` binds two handlers to `FWorldDelegates::OnWorldTickEnd`:
`OnWorldTickEndMask` at `:354` (invocation index 0) and `OnWorldTickEndSample` at `:355` (index 1).
Reverse broadcast ⇒ **Sample runs FIRST, Mask runs SECOND.**

- `SampleDeferredActiveState()` (`:3810`) fills `Snap->MaskValues` by searching
  `Async->MaskMeasure.GetRecords()` for `(Id, Target, StartFrame)` and **defaults to `0` when no
  record is found** (`:3841-3850`).
- The records are created by `EnsureMaskRecordsForCapturedFrame()` (`:849-864`), called from
  **`OnWorldTickEndMask`** at `:786`.

⇒ **On a fire's FIRST captured frame the record does not exist yet when the sample reads it, so
`mask_value` is 0. From the second frame on it exists (created the previous tick-end) and is correct.**

🔑 **THE CLASS SPLIT IS A CONSEQUENCE, NOT THE MECHANISM.** The gap lands on every fire's **first
fire-active captured frame**. For `FireWindow` ids that frame IS the first *labelled* frame, so the
zero is visible in `annotation.json`'s window. For `ActorHidden` ids (`blinking`) the first labelled
frame is the first *hidden* frame, which is later, so the zero lands on an unlabelled frame and is
invisible unless you read `labels.jsonl`. **The 4/4-vs-0/2 split is what this mechanism predicts.**

### §1.3 The confirming reading (RUN BEFORE IMPLEMENTATION, recorded here)
Predicate: *the `mask_value == 0` entry is each fire's first fire-active captured frame, and no other
entry carries 0.*

| session | first-active frames with `mask_value==0` | other rows with 0 |
|---|---|---|
| Lyra `LYRA_SMOKE_01` | **6 of 6** | **0** |
| StackOBot `B20_M45_FULL_NAT` (native order) | **6 of 6** | **0** |

⇒ **not host-specific, not tick-order-specific, and present in every banked session since `m43`.**
Journal 071 §11.2 saw one instance and called it sporadic; it is systematic.

### §1.4 What would FALSIFY this mechanism
- A `mask_value == 0` entry on a frame that is **not** a fire's first active captured frame → the
  cause is not record-birth timing. (Measured: 0 such rows on two sessions.)
- Swapping the two handlers' order (or serialising them explicitly) **not** removing the zeros →
  the record-birth ordering is not the cause.
- `mask_value` correct on a first-active frame **before** the fix → the reading was mis-taken.

### §1.5 The fix, and why it is structural rather than an order swap
⛔ **Rejected: swapping the two `AddUObject` calls.** That "fixes" it by relying on reverse-broadcast
order continuing to hold — an ordering guarantee this project has already ruled **cannot be
requested, only constructed** (journal 068 §8 / the P9 tick-order finding; `FTickableGameObject` has
no prerequisite API and the drain of `NewTickableObjects` reuses a LIFO free list).

✅ **Shipped: ONE `OnWorldTickEnd` handler that calls the mask block and then the sample block in
explicit, written order.** The two existing bodies are unchanged; only their sequencing becomes a
statement in our own code instead of a property of the engine's delegate container.
**PREDICTION: `mask_value` becomes non-zero on every fire's first active frame, on both hosts and in
BOTH tick orders, and no other label field moves.**

⚠ **Named risk of the reorder, and the gate that covers it:** the sample now runs AFTER the mask
block, so it sees post-mask state. `ComputeFireActive` reads `IsLogicallyHidden` / the anomaly's own
state; the mask block only writes `bRenderCustomDepth` / `CustomDepthStencilValue`
(`AnomalyStencilTag`) and never visibility. **PREDICTION: `FireActive` is unchanged ⇒ `frame_indices`
identical value-for-value.** `OBS-5`/`P-C7 v3` and `G-EDGE` are what would catch it if wrong.

## §2. `target_pixels` and `observable` — the shape being built

- `ServiceTargetMask` already computes the per-tag `Count` for its `MASK-TIE` line (`:1062`) and
  throws it away. `TargetMaskOutcome` becomes `TMap<int32, FTargetMaskOutcome>` carrying
  `{ State, TMap<uint8,int32> Counts }`.
- The **drain join** (`:3178-3206`), which already joins by `SessionIndex`, fills
  `Snap->TargetPixels[i] = Counts[(uint8)Snap->MaskValues[i]]`, i.e. **indexed by the SAME
  `mask_value` the row emits**, so the two cannot disagree by construction. `-1` when there is no
  outcome, no mask, or `mask_value == 0`.
- `observable[i] = null` when `TargetPixels[i] == -1`; otherwise
  `Active[i] && ConditionHeld[i] && TargetPixels[i] >= ObservableMinPixels`.
- `ConditionHeld[i]` from `IAnomaly::IsVisualConditionHeld()` (default `IsCurrentlyAnomalous()`),
  overridden by `missing_texture` / `corrupted_texture` to "every captured slot is still ours".
- Knob `IAI.Capture.ObservableMinPixels` / ini `[AnomalyCapture] ObservableMinPixels`, compiled
  default **1**, `G139` three-branch echo printing the per-mille equivalent for the written size.

**annotation.json v2:** `affected_frames` = the OBSERVABLE subset (+ `span_frame_count`);
`injected_frames` = today's subset unchanged; `observable_frame_count`; `unmeasured_frame_count`;
`observability_measured` (false ⇒ `affected_frames` falls back to `injected_frames`); root
`label_schema: 2`. Veto untouched; an event with zero observable frames STAYS.

## §4. `MPP_Outline` — the §0.4 read, answered BEFORE the legs

**ANSWER: ANY NON-ZERO.** `Content/Effects/Materials/PostProcess/MPP_Outline.uasset` carries
**`bEnableStencilTest`** (present in the tagged-property name table ⇒ non-default ⇒ **true**), while
**`StencilCompare` and `StencilRefValue` are ABSENT ⇒ engine defaults.** `StencilRefValue` has the
inline default `0` (`Material.h:940`); `StencilCompare` has no inline or constructor initialiser, so
it takes the enum's zero value, which is **`MSC_Less`** (`EngineTypes.h:774-783`). The engine's own
CPU mirror reads `case MSC_Less: bStencilTestPassed = (StencilRef < StencilValue)`
(`PostProcessMaterial.cpp:159`). ⇒ **the material runs wherever custom stencil > 0**, and selects no
particular value.

**The instrument proved itself both ways (`G96`)**: the same scan SHOWS `bEnableStencilTest`,
`BlendableLocation`, `MaterialDomain`/`MD_PostProcess` — all non-defaults — so its silence on
`StencilCompare`/`StencilRefValue` is a reading, not blindness.

⇒ **Every census-tagged actor (200..254) is inside `MPP_Outline`'s stencil test in frames the labels
call CLEAN.** ⛔ **`G120`: this says the material RUNS on those pixels, NOT that a pixel changed** —
the graph still edge-detects. But the 069 hazard is no longer hypothetical on this host.
⚠ Two caveats carried: the census preflight resolved `MaterialInstanceDynamic_365(depth+stencil)`,
and that it is an instance of `MPP_Outline` is **strong but circumstantial** (it is the only Lyra
post-process material reading both); and `bEnableStencilTest`/`StencilCompare`/`StencilRefValue` are
`UMaterial` properties, not parameters, so a MID cannot override them.

**CONSEQUENCE, EXECUTED: this brief's Lyra legs run with `IAI.Capture.Census 0`**, stated on every
Lyra result. **PROPOSED, NOT IMPLEMENTED:** a `StartRun` rule that, when the host-PP preflight finds a
custom-stencil reader whose stencil test admits the reserved range, **REFUSES the census (or warns
loudly and disables it)**. ⚠ **This matters for Bates too** — that host writes custom stencil on some
actors. Chat decides the refuse-vs-warn shape.
