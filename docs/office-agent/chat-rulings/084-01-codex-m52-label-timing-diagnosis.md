**Onset is controlled by a delayed CPU observation of an already possible render change.** `Capture:300` maps m52 to `AnomalyState`. `Capture:4955–4970` resolves the labelled predicate through `Injector->IsAnomalyCurrentlyAnomalous`. `Mip:892–906` implements it as `bActive && ANY held texture's GetNumResidentMips() < BaselineResidentMips`. It is neither the requested bias nor an acknowledgment from the frame being captured, and it does not wait for every texture. The budget-wait logic at `Capture:731–753` uses this predicate via `BurstAwaitsDeferredOnset` (`:4315–4344`). Labels and telemetry sample it again at world tick end (`:877–892`, `:4864–4906`).

The engine ordering explains why that is late:

1. Apply records baseline residency and raises `NumCinematicMipLevels`, calling `UpdateCachedLODBias` (`Mip:479–509`). The latter updates a CPU policy value (`Runtime/Engine/Private/TextureDerivedData.cpp:2765–2768`). `GetCachedLODBias` reports that cached policy, not completion of its visual effect. The streamer reads it in `Runtime/Engine/Private/Streaming/StreamingTexture.cpp:175–192`.
2. `UGameEngine::Tick` ticks the world at `Runtime/Engine/Private/GameEngine.cpp:1775`, dispatches viewport rendering at `:1891`, then ticks streaming at `:1901`. That is a GT ordering, not a synchronization guarantee between the residency mirror and the RHI texture a queued draw will use.
3. `UTexture2D::StreamOut` creates an asynchronous update (`Runtime/Engine/Private/Texture2D.cpp:1687–1702`). On the render thread, `FTexture2DUpdate::DoFinishUpdate` calls resource `FinalizeStreaming` **before** marking the request successfully finished (`Runtime/Engine/Private/Streaming/Texture2DUpdate.cpp:147–156`). `FStreamableTextureResource::FinalizeStreaming` replaces `TextureRHI`, updates its texture reference, and updates the render resource state (`Runtime/Engine/Private/Rendering/StreamableTextureResource.cpp:214–236`). Draw commands ordered after that update can sample the reduced texture.
4. `GetNumResidentMips()` for the relevant streamable texture returns **`CachedSRRState.NumResidentLODs`** (`Runtime/Engine/Private/Texture2D.cpp:481–483`). This mirror is updated only when `UStreamableRenderAsset::TickStreaming` later observes the pending update completed successfully (`Runtime/Engine/Private/StreamableRenderAsset.cpp:166–186`, particularly `:178`). The resource change therefore precedes its GT residency acknowledgment; there is no rule making those two observations belong to the same captured frame.
5. Streaming polling and submission are staged and asynchronous. `StreamingTexture.cpp:262–275` calls `TickStreaming` and copies the state. `Runtime/Engine/Private/Streaming/StreamingManagerTexture.cpp:1683–1754` distributes work over stages, with an additional in-flight poll at `:1740–1743`. `Runtime/Engine/Private/Streaming/TextureStreamingHelpers.cpp:257–260` defaults `r.Streaming.FramesForFullUpdate` to five. This is a scheduling parameter, not a fixed five-frame visual delay.

A valid sequence is therefore: render resource becomes low-mip; a captured view uses it while tick-end metadata still sees baseline; one or more later GT polls acknowledge it; a subsequent snapshot finally reads held=true. A roughly two-picture delay is mechanically plausible. The exact count depends on completion relative to sampling, streamer stage, worker/IO/RHI load, render queue progress, capture cadence, texture count and which texture materially affects the image. The bank's dominant one-frame error plus smaller earlier departures already falsifies a universal “subtract two” fix.

The subsequent first-label/first-differing-picture claim at `Design:443–446` rests on it. Dispatching rendering before the GT streaming tick does not stop **earlier asynchronous work** from changing a render resource independently of its GT mirror. The RT-before-GT-completion sequence above contradicts that inference.

**A proposed fix should attach rendering evidence to each captured frame and retain the event through restoration.** This is a design proposal for Chat's ruling, not an accepted implementation instruction.

The useful source-level signal is the **render resource's committed mip availability for the actual draw**, not `UpdateCachedLODBias`, `StreamIn` returning, a GT completion poll, or a fixed delay. `Runtime/Engine/Public/Rendering/StreamableTextureResource.h:37–42` explicitly declares `GetState()` coherent on the rendering thread; `:69–72` exposes its current first mip. For ordinary streamable 2D textures, `FinalizeStreaming` and `RHIUpdateTextureReference` at the engine locations above mark the resource transition. Other allocator paths also finish there (`Runtime/Engine/Private/Streaming/Texture2DMipAllocator_AsyncCreate.cpp:84–102`, `Texture2DMipAllocator_AsyncReallocate.cpp:100–108`). Partially resident RHI paths additionally change the first visible mip (`Runtime/Engine/Private/Streaming/Texture2DStreamOut_Virtual.cpp:36–43`, `Texture2DStreamIn_IO_Virtual.cpp:51–58`); a complete implementation must cover those operations and normalize mip indices to the same asset/platform coordinate system. Virtual-texture eligibility exclusions in `Mip:75–98` do not justify equating every RHI allocation's total mip count with the first sampleable mip.

The proposed contract has five parts:

1. **Separate request lifetime from observed lifetime.** Retain immutable event identity, target/render identities, resource generations and baseline mip state through Applying, Holding and Restoring. Ending the requested hold restores policy and initiates stream-in, but does not discard the information required to classify later captured frames. Baseline needs a stable render-resource observation, not merely a potentially stale GT count at Apply. Resource replacement and destruction need explicit lifetime handling; render code must not dereference mutable game-thread UObjects.
2. **Latch state on the rendering timeline for the exact captured view.** A small RT tracker can sample the coherent resource state at a draw-submission boundary, or engine transition hooks can publish versioned state for that boundary. For each held texture record its baseline and rendered first available mip. Where mip coordinates are consistent, degraded means current first mip is coarser than baseline; the resource-state predicate is ANY degraded texture, and baseline return requires ALL relevant textures back. The latch must describe the resources used by that family, not whatever state happens to be current in a later callback. An after-the-fact GT boolean or an unassociated RT callback recreates the problem.
3. **Join that receipt to RGB and masks by request, view/family identity and resource/event generation.** Buffer serialization until the asynchronous receipt arrives. Keep the original capture's index; do not shift rows by guessed amounts or attach a late receipt to the next GT frame. Per-frame state should determine membership even if streaming causes an interruption inside a nominal event. A single contiguous interval must not conceal such holes.
4. **Pre-arm the spatial evidence across both uncertain boundaries.** Tags and mask capture need to be available from Apply through restore completion, since waiting for a GT report of the first low-mip rendering is already too late to arm that picture. The render receipt then determines which evidence belongs to the event. The m26 budget should count eligible rendered observations. Mask lifecycle and event association must survive ordinary `LiveFires.Reset()`; changing only the label writer cannot recover mask pictures that were never armed.
5. **Make restoration a verified render transition.** Preserve tracking when a stream-out is in flight even if the cached GT count says baseline. Require an appropriate RT baseline acknowledgment and no pending anomaly-owned transition before retiring the restoration record. Keep timeout, takeover, destroyed-target and capture-cutoff outcomes explicit; none is proof of a restored picture. Waiting longer by a fixed number, changing the global streamer cadence, or shifting both edges by constants does not establish this contract.

There is an essential limit to what this low-cost engine signal proves. **Resident/available mip is not the mip actually sampled at each fragment, and neither alone proves a visible difference in the final RGB.** A material can already sample a coarser mip through derivatives, a flat texture can look identical, the target can be occluded, a shared resource can affect another object, and temporal processing can retain prior-image contributions. Opening on ANY below-baseline resource and closing on ALL restored resources solves the residency-window error, but cannot honestly be advertised as exact visible-pixel equality for arbitrary content. Nor does the `MipBiasFade` bookkeeping in `FinalizeStreaming` establish that the measured five-frame tail is a fade; ordinary asynchronous restoration already explains these examples, and no shader/final-pixel fade contribution was measured here.

If “visible” literally means final image change, the stronger design needs a render-derived observation of **affected, drawn samples** and their difference from baseline, with a defined significance threshold and treatment of temporal history. A material/sample diagnostic comparing normal versus clamped LOD, including depth ownership and propagation through the capture's postprocessing, or a controlled same-view counterfactual render, can provide that witness. Without such a witness, it is better to expose the exact rendered-resource state and a separate observable/unknown status than to repeat the previous by-construction pixel claim. These are distinct guarantees, and the acceptance gate should say which one it tests.

**The cheapest falsifier is already available offline; the cheapest qualification bench is a short controlled two-edge sequence.** The D/E `si=75` comparison falsifies first held == first visibly changed picture, and F-H `si=166..170` falsifies end-of-fire == first restored picture without any new run. For a proposed implementation, the smallest useful bench would use a fixed camera, an unlit opaque target with a fully established high-frequency or mip-coded streamable texture, a stable baseline/no-hold reference, and continuous captures through Apply, hold and complete restore. Initial qualification can disable temporal AA so a known mip change has an unambiguous image witness; the production temporal path is a separate required check before claiming final-RGB equality there.

The proposed gate would record, for every saved picture, request ID, actual view/family identity, GT stamp/counts, RT resource generation and mip state, event membership, and target-mask identity. It would compare pixels to the matched reference independently of the label predicate. For the controlled texture, a predeclared pixel criterion can identify both edges; there is no best-fit temporal shift and no tolerance that silently accepts the reported two-frame or five-frame mistakes. A one-texture case checks the basic edge. A two-texture case in which one restoration finishes later checks the ALL-restored close condition. Captures continue long enough to include a clearly restored negative tail; missing frames or missing masks at an edge are unassessable/failing evidence, not a pass.

The minimum can-fail cases are independently corrupted metadata with (a) onset delayed by two pictures and (b) offset advanced by five pictures, **moving label and mask membership together**. Each must fail the pixel-edge test. A no-hold negative remains useful, but it cannot test timing if nothing ever manifests. A delayed-restoration case should deliberately keep one visibly contributing RT resource low for at least five captured frames after the restore request; a separate delayed GT acknowledgment case should leave the rendered edge unchanged. A correct RT-based classifier follows the former and ignores the latter. These cases directly discriminate the proposed mechanism from the old GT predicate.

An independent view-identity check remains necessary to rule out m51 while validating m52. Native and synthetic capture order, then a short loaded/unpaced variant, can test whether the same proof survives timing changes. Repeating first-label == first-held, counting eventual `RESTORE VERIFIED` lines, or checking mask/label agreement would not qualify the fix. The existing bank offers a cheap failing baseline; no such new qualification run was performed in this read-only review.
