**F1 — P1: two baseline pictures do not establish that the old hold can no longer arrive.** `FTrail::Step` closes after two baseline results, independently of pending streaming work or a restoration generation (`Window:107–140`). `RevertSessionIndex` governs the timeout; it is not a completion fence. `ComputeRenderMembership` supplies only the residency verdict (`Capture:5663–5669`). Once closed, the trail stops contributing watches, fires and masks (`Window:154–156`; `Capture:5454–5459,5066–5072,1302–1307`).

The diff correctly repairs the anomaly's **restoration polling** for the already-back race: if the GT mirror is at baseline but streaming is busy, `Revert` keeps a restoring entry; `TickAlways` requires baseline **and no pending operation** before removing it (`Mip:885–914,1004–1014`). The capture trail does not consult that protection. An early revert can therefore leave a stream-out pending, produce two baseline captures while it is pending, close the capture trail, then draw the delayed low-mip resource in a later capture. The restorer will eventually request recovery, but the intervening blurred pictures have lost their event and mask. This is a source-permitted ordering, not a measured occurrence on the candidate.

**Proposed correction:** retain the event until restoration of its owned transition is acknowledged and a subsequent matching render receipt establishes baseline. Per-frame membership can remain out on genuinely baseline pictures while the event stays attached. A useful qualification case delays an outstanding stream-out beyond the two baseline confirmations, then lets it land after revert. The prior consult explicitly called for this distinction between frame membership and safe event retirement.

**F2 — P1: sorting one drain batch does not make trail updates sequential, and closure cannot recover from a late held receipt.** `Capture:4184–4192` sorts only the frames already collected in `Batch`. `SveCap:419–443` scans in-flight readbacks newest first and skips unavailable/delayed ones. Each completed frame is published separately under `CompletedCS` (`SveCap:518–521`); each GT pop separately takes that lock (`:533–542`). The GT can exhaust the currently published queue between two RT publications, splitting one RT drain across GT batches. The existing bench delays at `SveCap:442–443` are another explicit source of later-first delivery.

This receipt ordering is sufficient, with the default tail of zero:

| Receipt processed | Residency | Result |
|---|---|---|
| si 100 | Baseline | `CleanRun=1` |
| si 102, before si 101 arrives | Baseline | `CleanRun=2`, `bClosed=true` |
| si 101, delivered later | Held | Its own membership is held; `CleanRun` resets, but `bClosed` stays true |

In chronological order the sequence is baseline, held, baseline: there have not been two consecutive baseline frames. `LastProcessedSI` is only a maximum, not an ordering guard, and `Step` neither checks adjacency nor clears `bClosed` on held/unknown (`Window:107–140`). Thus future watches/fires can already be detached. A different later-first baseline ordering can also make an older baseline frame enter `SettleTail` even when the configured tail is zero, through `SessionIndex < FirstBaselineSI` (`:129`). A dropped SI likewise does not break `CleanRun`.

**Proposed correction:** advance the trail through an event-specific ordered receipt cursor, with explicit terminal treatment for missing earlier requests. Unresolved gaps must not count as clean confirmations. Per-frame receipt classification can be computed independently, but retirement and tail arithmetic need chronological evidence. A regression should split publication across batches, with baseline/held/baseline around the split; a same-batch sort test would miss this defect.

**F3 — P1: “no watched texture” is not proof that the captured picture is before Apply.** The final lead-in and post-gap ticks call `CaptureCurrentFrame()` before `BeginFire()` (`Capture:828–831,878–898`). The texture watch is frozen inside `CaptureCurrentFrame` (`:4865–4879`), whereas `FinalizeArmedLabel` copies the newly live fire later (`:5047–5050`). Consequently a drained snapshot can contain an m52 fire and no watch for that event. `Combine(...,0)` unconditionally returns `BeforeApply`, which becomes `Out` (`Window:46–50,72–79`); the drain then clears `FireActive`, `FireLabelled`, `ConditionHeld` and `stuck_mip.held`, and mask filtering removes the tag (`Capture:5663–5669,5708–5748,1467–1483`). This absence is not even counted by `RenderRecordMissingFrames`, whose increment requires a nonempty watch (`:5664`).

The normal packaged-engine Apply tick may indeed still render baseline: this Apply changes bias, and the ordinary engine streaming tick follows viewport drawing (`Mip:663–682`; `UE/Engine/Private/GameEngine.cpp:1888–1901`). I am **not** claiming that every ordinary Apply-tick picture is already blurred. The problem is the unproven invariant used to manufacture a clean result. `ConsumeWantedForPublish` takes the oldest pending request without checking its armed frame against the serving family (`SveCap:150–179`); cancellation checks only epoch/cut (`:116–130`). If that unwatched arm is not served until a later family after the mip drop, its blurred RGB still receives `before_apply` and an empty effective mask. No generation change is necessary for this case.

There is also no recovery of the original texture set when the anomaly becomes inactive outside `BeginRevert`: the getter refuses inactive anomalies (`Injector:838–845`; `Mip:1092–1106`). Any remaining live-fire snapshot then has the same empty-watch interpretation. The normal FSM revert is covered by its frozen trail; that does not prove all other lifecycle paths are covered.

**Proposed correction:** freeze the event and its texture watch together before the matched family is submitted, and validate the actual serving identity. A missing event watch should be explicit unknown/unresolved unless the code positively proves that this particular render predates the Apply. A delayed-family case is a useful can-fail proof; testing only normal continuously served arms would not establish that invariant.

**F4 — P1: purity is a registered-active-world snapshot, not the whole loaded world, and it is not maintained during the hold.** The new scan removes the visible-set and targeted-fire bypasses, which addresses the ordinary off-screen-user defect. But `BuildWorldTextureUsers` uses default `TActorIterator<AActor>` and expressly skips `!AC->IsRegistered()` (`Mip:46–61`). In this engine the default flags include `OnlyActiveLevels` (`UE/Engine/Public/EngineUtils.h:542`), and that filter tests level visibility/association and the active level collection (`:423–440`). A loaded inactive level is therefore outside the census. An unregistered component on an otherwise included actor is also outside it, although its material can already reference the held texture.

For registered actors in included levels, actor/component visibility is not tested. Primitive subclasses use their texture/material enumeration and decals have a separate branch (`Mip:64–76`): static, skeletal, ISM/HISM and landscape components are not excluded merely by component type. The per-texture requirement of exactly one target component is enforced, including targeted fires (`Mip:377–390,542–573`; `Window:160–188`). That is a meaningful correction, but it does not cure the omitted loaded users.

The census runs once during Apply (`Mip:430–452`). No new registration, level activation, spawn or material-change guard maintains it while textures are held or restoring. An omitted loaded component can register, or a new user can stream in, and display the same reduced asset while the event and mask still name only the original target. An after-the-fact restore request would itself have latency, so merely detecting the extra user after it has rendered would not meet a zero-wrong-object contract.

The independent `TEXUSERS` path has the **same registration blind spot** (`Capture:4677–4699`) and is invoked at fire time (`:4750–4763`). Its different iterator does not make that coverage independent. The harness's count comparison also does not join each enumeration to each held event/texture (`084-03-lib.py:218–225`).

**Proposed correction:** enumerate all relevant loaded components, including inactive levels and unregistered components with material references, with appropriate template/dead-object exclusions. Chat also needs a stated lifetime guarantee: for example, control admission of new users before they render, or isolate the affected texture per target. The gate needs inactive-level, unregistered-then-registered, and post-Apply user cases, including the restore trail. The m52 rule remains per held texture; the separate m53 all-slots rule should not be substituted for it.

**F5 — P1: unresolved restoration ownership is discarded at capture boundaries.** `FinishRun` reverts live fires directly, then clears refusals, actor reservations and all capture trails (`Capture:6118–6121,6761–6768`). `StartRun` also reverts existing injections before resetting render truth (`:3121–3124,3321–3332`). Neither path transfers the old held/restoring texture set into the new run or waits for render-confirmed recovery. The only getter for that set requires `IsActive()`, while `Revert` has already cleared `Held` and set inactive (`Mip:940–948`; `Injector:838–845`).

A stop/cut during an unresolved restore, followed promptly by another capture in the same world, can therefore save negative lead-in pictures of the still-blurred target with no m52 fire/watch. This also applies to starting capture while an earlier live hold is being reverted. Rejecting a new Apply as `not_restored` does not label those negative pictures. Furthermore, `stuck_mip_restore_unresolved_at_end` counts only trails that were already opened; a frame cap reached during a live positive window can revert without creating one (`Capture:811–824,6135–6146`).

**Proposed correction:** preserve restoration ownership outside the capture-run container until it is resolved, or make capture admission explicitly depend on resolution. A capture cutoff should record the unresolved live event as well as an already opened trail. The continuous-single-run timeout behavior is better than before; it is not a proof for stop/start or takeover boundaries.

**F6 — P2: m55 can permanently consume a fabricated negative or miss final queued observations.** The normal path queues m52 observations and patches membership from the render result. But the initial queued `bLabelled` is false (`Capture:5348–5352`). After more than 16 ticks, or on a forced flush, `FlushObserveQueue` sends that unchanged value when no result exists, increments `ObserveForced`, and removes the queue entry (`:5777–5814`). If the held RGB/receipt arrives later, the label/mask path can classify it held, but that m55 observation is no longer patchable. `Observe` is one-shot per pending item (`Change:75–77`). Missing knowledge has become an m55 negative rather than an explicit missing-receipt outcome.

There is an additional shutdown ordering issue introduced by deferring these observations: `FinishRun` calls `BeginClosure` before draining (`Capture:6111–6129`); `BeginClosure` immediately closes existing events (`ChangeStage:583–590`), and subsequent observations for those events are discarded as `late_event_observations` (`Change:82–83`). A manual stop/teardown with queued m52 receipts can omit valid final membership from the evidence even if the final RGB and labels drain successfully.

**Proposed correction:** preserve an explicit unresolved/failed observation outcome instead of submitting the provisional false value, and coordinate final closure with the ordered observation drain. Tests need a receipt delayed beyond 16 ticks and a stop with a known held observation queued. These are evidence-side failures; they should not be misreported as proof that the eventual `labels.jsonl` row itself remained false.

**F7 — P2: the deferred-mask age is reset whenever it is serviced, defeating the advertised timeout.** `ServiceTargetMask` moves the result out and removes its `FDeferredMask` (`Capture:1445–1449`), then creates a fresh entry when the render result is still absent (`:1460–1464`). `AgeTicks` has a default of zero (`:225–229`). Lost colour requests can retain full mask payloads until run cleanup, with no working per-entry timeout.

**Proposed correction:** retain the original entry/age, or use an immutable issue/deadline field. A missing-colour test should verify the actual terminal mask outcome and payload release. This is separate from the m55 queue, whose age does accumulate.
