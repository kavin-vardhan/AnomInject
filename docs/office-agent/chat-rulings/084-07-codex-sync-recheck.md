The implemented data flow is coherent for a known endpoint: `HeldLevelOf` supplies the value (`Anomaly_StuckLowMip.cpp:1302–1306`), both restoration branches preserve it (`:1011–1019,1031–1038`), live/restoring texture exports carry it (`:1315–1342`), and both watch-building paths copy it (`AnomalyCaptureSubsystem.cpp:5949–5959,6055–6065`). Membership processing classifies each texture and combines the levels (`:6863–6883,6902–6911`). A member receives `ReasonPartial` independently of temporal AA (`:7322–7327`); telemetry exposes the flag and each endpoint/level (`:7358–7361,7380–7388`). Thus a fully observed set whose textures are all at or below the declared held endpoint gets **no partial flag**, on either edge. The normal offset path retains the event's texture set rather than looking only at the still-low primary texture.

There are three qualifications:

- **N4, medium — uncertainty is described as proven partial application.** `IsPartialHeldSet` treats an `Unknown` texture as short of held (`AnomalyStuckMipWindow.h:677–692`). A known-held texture plus an unavailable sample therefore gets `partial`, even if the unavailable texture is actually fully held too. The new selftest explicitly endorses this at `tools/m52_window_selftest.cpp:1477`. Conversely, an unknown/invalid held endpoint (`HeldLevel <= 0` or `>= Baseline`) turns every known below-baseline count into `AtHeld` (`AnomalyStuckMipWindow.h:670–674`; selftest `:1479`), so a genuinely intermediate level can go unflagged. These are deliberate fallback choices, not evidence that the record proves a partial set. An all-unknown member is also passed to `FPartialEdgeTrack` as nonpartial/full (`AnomalyCaptureSubsystem.cpp:7324–7327`; `AnomalyStuckMipWindow.h:721–725`), potentially misplacing later frames between onset/mid/offset. Proposed correction: distinguish known full, known partial and unresolved state; an unresolved member should not establish a full-set boundary or receive the same evidentiary exemption as a proved partial set.
- **The endpoint is a prediction, not the measured eventual residency.** `PredictMaxAllowedMips` uses cached resource LOD bias only (`Anomaly_StuckLowMip.cpp:191–195`); it is frozen at application (`:772–796`) and clamped by `HeldLevelOf`. UE additionally accounts for cinematic/forced-resident policy, `bUseAllMips`, global and budget mip bias, platform modifiers and optional-mip availability (`UE/Source/Runtime/Engine/Private/Streaming/StreamingTexture.cpp:182–233`), then separately chooses wanted residency (`:310–329`). For example, if the plugin declares endpoint 7 while the effective streamer endpoint is 5, a sample of 7 is called full before that deeper drop finishes. The banked floor-7 cases do not demonstrate equivalence under those other settings. Proposed correction: qualify the endpoint against effective streaming policy, or define and enforce a narrower supported endpoint contract. A missing endpoint is not proof of full application.
- **N5, medium — the summary cannot name every flagged frame.** `FPartialEdgeTrack::Cap` is 32; further partial frames only increment `PartialOverflow` (`AnomalyStuckMipWindow.h:706–746`). The run total includes overflow, but onset/mid/offset counts, maxima and frame lists use only the stored indices (`AnomalyCaptureSubsystem.cpp:8318–8345`). Forty onset-partial frames produce total 40, onset 32 and only 32 named indices, plus the word `overflow`. That fails the report's “every flagged frame is identifiable” claim and is material now that partial duration has no three-frame ceiling. Proposed correction: preserve all indices, or use exact ranges/counts with a complete separately referenced record. Unknown members also need separate handling as above.

The source still emits `_events_over_three` and logs “MORE THAN 3” (`AnomalyCaptureSubsystem.cpp:8327–8350`; `AnomalyLabelWriter.cpp:972`). Those are stale diagnostics relative to the later ruling, not a source-side failure gate. The gate must apply the newer null-band and greater-than-eight investigation rules. Also, a single `Between` texture can legitimately trigger the source flag without any texture already at its final endpoint; the later ruling's special exemption for **flagged-invisible** frames still requires its own at-held witness. The existence of `partial` alone does not satisfy that exemption.

**2. camera_clipping: the chosen confirmation mechanism exists, but has an additional geometric miss and limited authority.**

The 16×9 global grid and 4×4 footprint grid are implemented with limits of 16 candidates and 320 traces (`AnomalyNearClipSlab.h:423–431`). Segments run between the two near planes and are clipped further to the candidate box (`:515–543,573–591`). The callback uses that component/instance body's complex trace (`AnomalyViewport.cpp:1274–1282`). Unconfirmable, over-cap, trace-capped and no-ray candidates retain a positive SAT result with uncertainty when no confirmed hit exists (`AnomalyNearClipSlab.h:494–503,600–631`). The snapshot carries the diagnostic and reason (`AnomalyCaptureSubsystem.cpp:5575–5582,5650–5656`). A confirmed hit beside an unconfirmable candidate establishes the existential positive and intentionally clears the frame-level uncertainty; this matches the stated implementation.

**N2, high — a planar render/collision mesh in the slab can become a clean negative.** Consider the selftest camera/slab (depths 10 to 100), and a wall at x=50 with actual local/world half-extent `(0,200,200)`. The SAT admits it. `ClipSegmentToBox` accepts `T0 == T1` (`AnomalyNearClipSlab.h:350–367`), so all 144 global rays become zero-length point segments before the callback. UE's `FBodyInstance::LineTrace` forwards to `LineTrace_Geom`, which only traces when length exceeds `UE_KINDA_SMALL_NUMBER` (`UE/Source/Runtime/Engine/Private/PhysicsEngine/BodyInstance.cpp:3536–3541`; `.../Experimental/PhysInterface_Chaos.cpp:989–991,1072`). Every query returns false. Because `Foot` was incremented before tracing, the footprint grid is skipped and the outcome becomes `Miss`, with `bPositive=false` and `bUnconfirmed=false` (`AnomalyNearClipSlab.h:532,560,602–631`).

This is not the documented sub-grid sliver: the wall covers the entire view and every global ray intersects its surface. The current wall selftest artificially gives its perfectly planar triangles a 0.5 cm half-thickness (`tools/camera_clipping_slab_selftest.cpp:757–762`), masking the defect. The independent arithmetic reproduction in `review-evidence.json` produces 144/144 zero-length segments. Proposed correction: retain nondegenerate slab-confined trace intervals, or robustly pad candidate clipping within the slab and handle degenerate intersections explicitly. A zero-length/unsupported query should not certify absence.

The broader answer to “exactly what the renderer draws” is **no**:

- `ResolveConfirmTarget` checks skinned type, body availability, raw collision complexity and presence of cooked triangles, but not render/collision mesh equivalence, render LOD, WPO, opacity masks, translucent opacity, Nanite geometry or material sidedness (`AnomalyViewport.cpp:590–627`). UE supports a distinct complex collision mesh and a selected collision LOD (`UE/Source/Runtime/Engine/Private/StaticMesh.cpp:6935–6940,6956–6960`). Thus a hollow rendered mesh with a solid simplified/custom complex mesh can still return an **unflagged** false positive; rendered geometry absent from the collision mesh can return an **unflagged** negative. The journal acknowledges collision-mesh and material-opacity limitations at `docs/sessions/2026-09-29-084-07-sync-fixes-round3.md:73–75`; that limits the “actual surfaces” claim rather than solving it.
- Chaos ray backface culling is set from `bDoubleSidedGeometry`, not from the rendering material (`UE/Source/Runtime/Engine/Private/PhysicsEngine/BodySetup.cpp:716`; `.../Experimental/ChaosInterfaceUtils.cpp:300`; `UE/Source/Runtime/Experimental/Chaos/Private/Chaos/TriangleMeshImplicitObject.cpp:162–174`). A two-sided rendered interior with one-sided collision, or the reverse configuration, can disagree. Starting inside a hollow mesh is therefore not generally equivalent to the double-sided mathematical triangles in the selftest. There is no separate “inside solid” treatment; this remains a surface-ray query.
- The landscape UPROPERTY route is correctly identified: `ULandscapeComponent::CollisionComponent` really is a lazy object property (`UE/Source/Runtime/Landscape/Classes/LandscapeComponent.h:453–455`). The body has a complex heightfield shape (`UE/Source/Runtime/Landscape/Private/LandscapeCollision.cpp:319–335`). But `CollisionMipLevel` is configurable (`UE/Source/Runtime/Landscape/Classes/LandscapeComponent.h:516–522`), so “heightfield is exact” means exact to that collision heightfield, not necessarily to the rendered landscape LOD/WPO. The early landscape return in `AnomalyViewport.cpp:597–606` bypasses the later collision/complex eligibility checks. The generic branch also compares raw `CollisionTraceFlag`; UE resolves `CTF_UseDefault` through `GetCollisionTraceFlag()` (`UE/Source/Runtime/PhysicsCore/Private/BodySetupCore.cpp:46–49`). Therefore the claim that every unsupported path is classified before tracing is too broad.

Proposed disposition for these content cases: either establish a supported render/collision contract and flag violations, or use an oracle that observes rendered geometry. This is a qualification of the accepted collision approach, distinct from N2's concrete implementation defect. No independent proof of Nanite/material/landscape equivalence is present.

The caps safely bound actual trace calls and fail conservatively for an otherwise unproved boolean decision. They do **not** bound scene enumeration, full ISM scans or the candidate arrays/name construction before confirmation (`AnomalyViewport.cpp:1083–1105,1175–1181,1246–1267`). The fraction uses all global rays as denominator even if the trace cap prevented testing some; footprint-only positives can have fraction zero (`AnomalyNearClipSlab.h:550–595,631`). It is a sampled diagnostic, not measured clipped-pixel coverage. The 0.5 ms in-engine cost requirement is still UNRUN; the timer at `AnomalyViewport.cpp:1267–1284` covers confirmation after candidate construction.

**N3, high — rotated instances under nonuniform component scale can still be rejected before confirmation.** `GetInstanceTransform(..., true)` composes two `FTransform`s (`UE/Source/Runtime/Engine/Private/InstancedStaticMesh.cpp:3402–3407`). For positive scales, UE multiplies scales componentwise and rotations separately (`UE/Source/Runtime/Core/Public/Math/TransformVectorized.h:1593–1616`); this is not generally the same as multiplying the instance and component matrices. The renderer applies the instance transform followed by the component matrix (`UE/Shaders/Private/LocalVertexFactory.ush:764–771`); engine instance bounds likewise use the matrix product (`UE/Source/Runtime/Engine/Private/InstancedStaticMesh.cpp:2662–2669`).

Concrete case: mesh half-extent `(10,10,10)`, local instance rotation 90° around Z, component scale `(10,1,1)`, component translation `(150,0,0)`, slab depth `[10,100]`. Rendered x extent is `[50,250]`; the box made from the composed `FTransform` has x extent `[140,160]`. The component broad phase admits the rendered bound, but the new per-instance SAT rejects it. HISM can select the correct index and still fail at the same final SAT. Even a NoCollision instance never reaches uncertainty classification in this case. `review-evidence.json` records the corner arithmetic.

Proposed correction: construct a conservative world bound from the actual matrix-composed corners, or support a general transformed parallelepiped; do not assume one orthogonal TRS decomposition encloses the rendered instance. The current F2 selftests use a single supplied TRS and omit component/instance composition (`tools/camera_clipping_slab_selftest.cpp:838–872`). This is a remaining F2 defect, not a claim that the old query handled this case correctly. The inherited camera cache also still omits geometry revision (`Anomaly_CameraClipping.cpp:164–179`), so same-frame mutations are not newly proven by the query fix.

**N7, medium — a restored holder can disappear from the verification census before it is checked.** Suppose a component initially has stencil value V with custom depth off. On snapshot rows, `labelled` is set to normal emission AND `FireActive`; transition-only/detached entries get false (`AnomalyLabelWriter.cpp:264–268,280–296`). `visible_positive` counts only such labelled entries with a valid box (`:274–301`). **N1, high — the new field reads a bit that was never the annotation authority for FireWindow events.** The policy table assigns `missing_texture`, `corrupted_texture`, `null_effect`, `solid_swap`, `lighting_mismatch`, `lod_corruption` and `time_dilation` to `FireWindow` (`AnomalyCaptureSubsystem.cpp:544–562`). `ComputeFireActive` only handles `AnomalyState` specially; every other source returns “actor exists and is logically hidden” (`:7551–7568`). Therefore an ordinary visible texture anomaly gets `FireActive=0`. Before 084-07 that did not remove its annotation membership: FireWindow events use `AffectedFrames`, independent of the activity bit (`:8882–8905`). The new writer now treats that same zero as `labelled=false` and suppresses its visible-positive status.

This affects both sync (`:5191–5194`) and async (`:5723–5734`). It also creates an explicit downstream disagreement: `IsFireLabelledThisFrame` returns true for FireWindow (`:5842–5860`), `FireLabelled` feeds m55 (`:5805–5820`), and target-mask arms use that policy (`:1497–1513`). A texture row can therefore say `labelled:false`, `visible_positive:false`, and still have `observable:true`, a positive mask and a positive annotation/m55 observation. `label_active_unlabelled_entries` also misclassifies these as nonmanifest families (`:7025–7027`).

Historical concrete exemplars are `M52SYNC_REAL_MT_R1_A1/session_20260929-022403/labels.jsonl:4` and `M52SYNC_REAL_CT_R1_A1/session_20260929-022615/labels.jsonl:4`, each SI 3, valid box, observable true and 21,039 target pixels. Each earlier leg has 112 visible-positive rows and no outside-annotation family. Applying the new source's ordinary unhidden FireWindow branch predicts the regression; these old files are **not** claimed to contain 084-07 output. Proposed correction: define one complete per-source membership policy, including FireWindow, and use it consistently for the row, injected-frame accumulation, masks and m55. A writer/integration check over the registered source families would catch this immediately; the current selftests never invoke this writer.
