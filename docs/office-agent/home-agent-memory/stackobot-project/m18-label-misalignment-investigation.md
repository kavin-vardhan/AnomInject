2026-07-15 INVESTIGATION TURN (report only, no fix, no commit). Base: plugin **`e2c6dd2` = tag `m17`**, in sync with origin. See [[concorde-smoke-bugs-investigation]] and [[anomaly-injector-state]].

**MECHANISM PINNED (candidate (a) CONFIRMED, (c)+(d) REFUTED):** `CaptureCurrentFrame()` stamps the label from `Auto->GetLiveFires()` at **mid-tick N** (AnomalyCaptureSubsystem.cpp:922-925 async / :963-976 sync), then `BeginFire()`/`BeginRevert()` mutate world state **later in the SAME Tick** (the switch at :269-272 LeadIn, :279-282 Positives, :289-311 PostGap → BeginFire :876-890 / BeginRevert :892-900). The **async** capture grabs the render of the **arm tick N** (proven empirically: the transition-tick frame's pixels contain the post-transition state), so label = pre-transition state, pixels = post-transition state.
- **FIRE edge** (last lead-in/post-gap frame, idx 3,15,27…): labeled clean, pixels ANOMALOUS = **false negative / contaminated negative** (worse for training).
- **REVERT edge** (last positive frame, idx 11,23,35…): labeled positive, pixels CLEAN = **false positive**.
- Real example (session_20260715-121622, m17 binary): frame_00003 (gframe 31845) anomaly_present=false, region diff 22.6 (checker visible); frame_00011 (gframe 31855) anomaly_present=true + valid bbox, diff 3.1 (clean).
- **(c) settle-K REFUTED as cause** — K protects the FAR side (first positive is 3 ticks after Apply); the bug is the NEAR side, the frame armed in the transition's own tick. Settle-K symmetry intact, NOT the fix site.
- **(d) REFUTED as stated** — Apply/Revert do NOT take effect a render-frame later; a change at end-of-tick-N lands in frame N's own render. Render-thread lag is a THREAD lag, not a state lag.

**SCALE CONFIRMED:** exactly 1 frame per boundary, BOTH boundaries. Steady-state fraction = **2 / (PositiveFrames + PostFrames)** = 2/12 = **16.7%** at defaults (pre=4 positive=8 post=4 K=2). Independent of SettleFrames (settle frames aren't captured) and of PreFrames (first burst only). Measured: 17/100 frames (9 FN + 8 FP) over 8 bursts. **Config-dependent — e.g. positive=30/post=10 → 5%.**

**Q5 / L=0 — this is NOT a new bug in the lag model, it's the model never being re-derived for async.** L=0 is CORRECT for the **sync** path (m7/G41 validated with a moving eyeball): sync `ReadPixels` returns the **previously presented** frame N-1, and the view sampled at the capture tick is also camera N-1 → they pair. The **async** path (added later, now default) captures the render of tick **N** — one frame later in content — and neither the state snapshot nor the view ring was re-derived. Boundary label bug = the STATE half (visible only where state changes = 2/burst). **PREDICTED, NOT MEASURED: the bbox/view is 1 frame stale on async for EVERY frame under camera motion** (ProjectionView :852-861 ring.Last() = camera N-1 vs pixels = camera N; SampleViewThisTick :863-874 runs before the capture in the same tick). Menu scene has a static camera → this turn's data cannot show it. **Must be checked as part of m18.**
NOTE the sync leg (sync = frame N-1) is CODE-DERIVED + backed by the historical G41 validation — it could NOT be pixel-measured this turn (see black-frames finding below).

**Q4 hide vs non-hide — BOTH affected identically (2/burst); the frame_indices gating just changes which list is poisoned** (:1280-1281 `bHideType = HiddenIndices.Num() > 0 ? HiddenIndices : AffectedFrames`):
- non-hide (missing_texture/lighting/LOD) → `AffectedFrames` (:1242, added whenever a fire is live at stamp + bbox projects): revert-edge frame wrongly INCLUDED, fire-edge frame wrongly OMITTED.
- hide-type (blinking/missing_object) → `HiddenIndices` (:1251, from `FActor->IsHidden()` sampled at :931 async / :972 sync): same 2-frame error (missing_object hides at BeginFire = end of tick).
- **EXTRA RISK for blinking (predicted, unmeasured):** it toggles hidden state inside the INJECTOR subsystem's own tick; the flag is sampled at the CAPTURE subsystem's tick. Two `UTickableWorldSubsystem`s have no guaranteed relative order → if the injector ticks AFTER the capture, EVERY blink toggle edge is misattributed on async, not just burst edges.

**NEW FINDING (3rd silent-corruption bug, same family): the SYNC capture path writes 100% BLACK frames in a packaged build.** `IAI.Capture.Async 0` + package → every PNG mean=0.00 (measured; async same scene/binary = mean ~112). Root = identical to Bug 1: sync goes through `AnomalyPreview::CaptureGameViewportRaw`→`FViewport::ReadPixels` (AnomalyPreviewCapture.cpp:31) → packaged viewport has no render target → D3D12 zero-fill "success". **So: a packaged sync capture silently produces a black dataset with perfectly plausible labels; and async is the ONLY working capture path in a package (load-bearing, not a fallback).** Also blocked the sync A/B for the alignment question. Fix options: re-plumb sync onto the backbuffer too, or make it refuse/warn loudly in packaged builds.

**FIX SHAPE (reported, not built) — the mechanism dictates fixing the TRANSITION TIMING or the ASYNC STAMP, never the label span:**
- **(A) minimal/surgical:** give each phase transition its OWN tick — check `BeginFire()`/`BeginRevert()` at the TOP of the phase case, before `CaptureCurrentFrame()`, so no frame is ever armed in the same tick as a state change. Path-agnostic, fixes both boundaries on async, leaves sync correct, does NOT touch L or settle-K (K still follows each transition; symmetry preserved). Costs 1 extra tick per transition (2/burst; no extra frames, no label-semantics change). Does NOT fix the predicted view staleness.
- **(B) root:** defer the async snapshot by one tick — stamp state+view for arm-id N at the top of tick N+1 (state at start of N+1 == end of tick N == what frame N rendered; view sampled at tick N+1 == camera N == what frame N rendered). Fixes the boundary error AND the view staleness in one change; sync + its validated L=0 untouched. More invasive (PendingSnapshots filled one tick late).
- **Do NOT "shift the label-span boundary by one"** — that would fudge the state alignment by lying about the span AND would BREAK the sync path, which is currently correct.
