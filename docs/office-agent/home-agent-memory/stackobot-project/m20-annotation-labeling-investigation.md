2026-07-15 INVESTIGATION (report only, no fix, no commit). Base: plugin **`c8aa3fa` = m19**, in sync. See [[m18-label-misalignment-investigation]].

**AUDIT HEADLINE — the brief's premise is WRONG: m18 DID reach annotation.json.** `AccumulateFrameEvents` (AnomalyCaptureSubsystem.cpp:~1300-1340) is called from `ProcessCompletedFrames` with `Snap->Fires`/`Snap->FireHidden` — the SAME snapshot `FinalizeArmedLabel` corrects. There is **no independent uncorrected range computation**; one accumulator + one writer feed every range. So "m18 leaked to other consumers" did not happen.

**BUG A (missing_texture range shift) — DOES NOT REPRODUCE. Do NOT "fix" it.** Measured per-frame on m19 (session_20260715-162507): annotation `frame_indices [3..10]` == pixels-corrupted `[3..10]` == labels present `[3..10]`, **zero disagreement**; annotation index 3 ↔ `frame_00003.png` ↔ visibly checkered. **Prime explanation = 0-based vs 1-based numbering.** Whole pipeline is 0-based (`frame_%05d.png`; encode_watcher.py docstring :17-18 "Frame numbering is session-local 0-based"), so a 1-based video player shows annotation index 15 as "frame 16" = exactly the owner's reported +1. **Corroboration: PRE-m18 the annotation was one LATE, which accidentally MATCHED a 1-based reading; m18 made it 0-based-pixel-exact, which BREAKS that reading — so the "regression" is m18 working correctly.** Shifting +1 would re-introduce the m18 bug. ASK the owner how "actual 16..20" was determined; if the client wants 1-based indices that is a SPEC change (all indices + docs), not a bug fix.

**BUG B (blinking) — REPRODUCES, but it is NOT a tail clip: it is a ONE-GAME-TICK-STALE sample on EVERY blink edge.** Measured (session_20260715-183542): **annotation(gframe G) == pixels(gframe G-1)** for every verifiable frame — e.g. annotation hidden `{4,5,6,10}` vs pixels hidden `{4,5,9,10}`; both edges late by exactly 1. **Mechanism: blinking toggles inside the INJECTOR subsystem's Tick (`AnomalyInjectorSubsystem.cpp:169-173` → `Pair.Value->Tick()`), a DIFFERENT `UTickableWorldSubsystem` that ticks AFTER the capture subsystem**, so `FinalizeArmedLabel`'s `IsHidden()` sample (end of CAPTURE's Tick) predates the toggle, while frame N renders with it. **This is exactly the risk I flagged as unmeasured in m18/G78 — now measured.** `missing_object` is immune because its hide runs in `Apply` ← `BeginFire`, INSIDE our Tick, before the sample (m18 G3: 0/100). ⇒ hide-type splits: **Apply/Revert-driven = correct; self-ticking (blinking, and by extension lod_popping) = one tick stale.** At a burst tail this reads as "last hidden frame missing".

**BUG C (subtype) — two halves, site `MapAnomalyToClient` (AnomalyCaptureSubsystem.cpp anon namespace):** `blinking → type "blink", subtype = (Transitions <= 2) ? "disappear_reappear" : "flicker"`; `else → type = Id, subtype = FString()` ← the empty "" for missing_texture (trivial: mirror the type). **Blinking 'flicker' did NOT reproduce as a miscount locally** — my blink genuinely has 3 transitions (2 hidden blocks per 8-frame window) so 'flicker' is arguably right for that config. **But there IS a code-proven order-dependence:** `Transitions` is counted incrementally via `LastHidden` in ARRIVAL order (`:1337`), and `Drain_RenderThread` fills `Completed` iterating `InFlight` in **REVERSE** (`AnomalyFrameCapturer.cpp:128` → `:164`) while `PopCompleted` is FIFO (`:184`) — so any drain with ≥2 ready frames (common at DrainTail/hitches) hands them to the accumulator NEWEST-FIRST → out of session order → spurious transitions → inflated → "flicker". **B and C are NOT one root:** B = stale sampling (tick order), C = order-dependent counting (drain order); a uniform stale shift preserves the transition COUNT, so B cannot explain the owner's 'flicker'.

**BONUS BUG FOUND (not reported by owner): `frame_count` is a SPAN, not a count.** `Count = End - Start + 1` (AnomalyLabelWriter.cpp:349). For gapped hide-type sets it lies: measured `frame_count: 7` with only 4 `frame_indices`; owner's example would give 8 vs 5. Non-hide (contiguous) hides the bug. Fix = `FrameIndices.Num()` or rename to `frame_span` (owner call).

**FIX SHAPES:** A = no code fix, confirm convention first. B = sample self-ticking state AFTER all subsystems tick — cleanest is deferring the snapshot to the start of tick N+1 (m18's option B, which subsumes m18's fix and covers any post-capture mutator); MUST re-run the m18 gate (align_check 0/100 + missing_object) since it touches the validated path. C1 = make Transitions order-independent by computing it at write time from the sorted per-event frame sequence, not incrementally on arrival. C2 = `OutSubtype = Id.ToString()` in the else branch.

Delivery session_20260715-192822 (genuinely delivery: no labels.jsonl, no run.json, file set = Actual_Frames+annotation.json+run_summary.json): annotation `[3..10]`==pixels, `[15..22]`==pixels. **Code proof there is no alternate route:** `bDeliveryMode` gates ONLY run.json (:604), the label-RECORD write (:816 async / :955 sync → LabelWriter :121/:247), and a run_summary flag (:1255). **`AccumulateFrameEvents` (:802) — which builds annotation's ranges — is NOT gated**, and the image is written with the SAME `Snap->SessionIndex` that feeds the annotation, so filename and range cannot diverge within a build. m20's Bug B fix also verified frame-exact IN DELIVERY (blinking `{4,5,9,10}`==pixels).
