## 1. What 080-05 established, in one paragraph

`FAnomalyMaskMeasure::ArmIfMeasurable` is called every tick-end, unconditionally
(`AnomalyCaptureSubsystem.cpp:894`), a record is created for every live fire
(`EnsureMaskRecordsForCapturedFrame`, `:1085-1100`), an event gets **at most 4 arms ever**
(`MaxArmsPerEvent = 4`, `AnomalyMaskMeasure.h:47`), and `ArmIfMeasurable` arms the **first** eligible
record each tick and returns (`AnomalyMaskMeasure.cpp:262-303`). ⇒ an event's entire arm budget is
spent on the four ticks after its record is created. For a **deferred-onset** anomaly the labelled
window does not open until the hold is measurably down — measured at **19–22 captured frames** of
pre-roll — so **100 % of the veto's evidence is gathered before the anomaly has engaged.** The veto
decides whether to delete an event from `annotation.json` using frames that are, by construction, not
the event's frames. That is the defect this unit fixes.

⚠ **It is a mismatch `R1` INTRODUCED**, and it is scoped to `stuck_low_mip` by construction:
`HasDeferredOnset()` is overridden in exactly one place (`Anomaly_StuckLowMip.h:22`), the default is
`false` (`IAnomaly.h:34`).

⛔ **080-05 §5 stands: the mechanism of the observed ZERO is NOT ESTABLISHED.** Five candidates were
excluded by measurement and the decisive datum — what the reduce table actually contained — **was
never logged**. This unit does not claim to explain that zero. It does two separate things: it moves
the evidence onto the right frames, and it makes a future zero readable.

## 2. The change as designed

**(a) The gate.** `FAnomalyMaskRecord` gains `bAwaitLabelled` (set once, at record creation, from
`Injector->DoesAnomalyHaveDeferredOnset(F.Id)`) and `bLabelledThisTick` (set every tick-end, before
the `ArmIfMeasurable` call, from the **same** `IsFireLabelledThisFrame(F)` predicate the label
snapshot uses at `:4721`). `ArmIfMeasurable` skips a record that is awaiting its window and is not
labelled this tick, beside the existing `ArmsIssued` / `bKnownUnmeasurable` guards.

🔑 **The budget needs no separate handling.** `ArmsIssued` only increments when an arm is actually
issued, so skipping an ineligible tick *is* the deferral — the four arms land on the first four
eligible ticks, which is what "the budget counts from the first eligible tick" means.

⚠ **The gate is also right at the other end, and that is deliberate:** a record whose fire has ended
is not labelled either, so leftover budget cannot be spent on a **restored** object. Measuring a
restored texture and calling it the event's evidence would be the same defect mirrored.

**(b) The log.** Two new lines.
- `M26 REDUCE-TABLE` — on every **contributing** frame, the full contents of that frame's per-tag
  reduce table (`tag:count` for every tag present), beside our own tag's count. This is the datum
  080-05 §5 could not recover. **It is emitted on EVERY contributing frame, not only on zeros**,
  deliberately: §5's decisive comparison was a NONZERO event against a ZERO event on the same actor,
  and a zero-only log would have supplied one half of it.
- `M26 VETO-READ` — one line per event as the veto loop reads its record, **admitted and vetoed
  alike**, carrying `tag / arms / resolved / maxCount / counts=[per-arm counts]` plus state,
  manifested and the deferral count.

**(c) The lever.** `IAI.Bench.VetoArmUngated <0|1>`, default **0** (gated), console only, no ini key,
takes effect BETWEEN RUNS, echoed at `StartRun` (A48). ON restores the ungated arm **exactly** — it
short-circuits the gate itself rather than faking the labelled bit, so the can-fail leg is the old
behaviour and not an approximation of it.

⛔ **`ArmProbeOnHidden` is deliberately NOT gated.** It requires `IsLogicallyHidden(Actor)`, which is
the `m45` hidden-class registry (`blinking` / `missing_object`); `stuck_low_mip` is `AnomalyState`-
sourced and OVERRIDE-1 gives one anomaly per actor, so it can never select a deferred-onset record.
Gating it would risk retiring the `F-6` item-5 liveness probe for no measured gain.

## 3. Predictions, fixed before any leg

### The comparison method, and one thing the brief asked for that cannot exist

The brief asks G-A/G-B to compare **`M26 VETO-READ` arm ids** across binaries. **That line is new, so
the A-side binary cannot emit it.** Stated rather than quietly substituted. What *is* comparable on
both binaries, and is the same quantity, is:

1. the **`M23 ARM` id offsets** from each record's `StartFrame` (absolute ids are `GFrameCounter` and
   carry run-to-run startup variance — the offsets are what the mechanism determines);
2. the **`M26S1 EVENT`** summary per event — `state`, `maxCount`, `arms`, `resolved` and all eight
   buckets;
3. **`run_summary.vetoed_events`**.

⚠ **And a bare A/B is not sound on its own.** These are MainWorld legs with no `B1`. I therefore run
a **same-binary CONTROL PAIR first** to establish the run-unique set empirically, and the cross-binary
difference set must be a **SUBSET** of it (the `G-S3a-1` / `P-C7 v2` method). Any extra field FAILS.
**A leg is never re-run for a better number.**

### G-C — the `stuck_low_mip` auto-pool leg, the `M52E_G7_YIELD` recipe

MainWorld, **600 frames**, seed 777, `IAI.Auto.Pool all 0, IAI.Auto.Pool stuck_low_mip 1`, native

1. **every `M23 ARM` request id belonging to a `stuck_low_mip` record lies INSIDE that event's

> **PREDICTION.** (1) holds; (2) holds; (3) holds. ⚠ **AND A PREDICTION THAT CUTS THE OTHER WAY,

> that is a RED on this gate and a much sharper question, and the new `M26 REDUCE-TABLE` and
> `M26 VETO-READ` lines are what make it answerable — which is the second half of this unit's point.
