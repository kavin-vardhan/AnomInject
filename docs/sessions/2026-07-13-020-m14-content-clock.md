## Goal
Fix the owner-observed bug: dashboard-driven StackOBot captures (m12 binaries) produced mp4s that play
`speed_ratio`× SLOW (120 @ 60, sustained 11.64 → stamped 11.64 → ~10.3 s, ~5× slow). Diagnosis (accepted
prior turn): the m11 honest stamp is CONTENT-CLOCK-DEPENDENT and picked the wrong clock for game-clock
content. m14 adds a setting that selects the clock. Fix Shape 1 ONLY (H-B refuted → no preview-pause; no
auto-adopt).

## OWNER OVERRIDE at commit — default = game (2026-07-13), and the open mixed-clock question
The m14 plan specified default **wall** ("the client ships real-time titles"). The owner overrode this to
**game** with new evidence and is validating both modes on the real office machine next:
- StackOBot is uniformly game-clock and game mode is verified correct here.
- The office titles (Until Dawn, Concorde) showed BOTH signatures: FAST at ratio ≈ 2 (real-time-driven
  parts, original Issue-2) AND SLOW at `Fps` 120/240 (game-clock world motion). That is MIXED-clock, and
  which mode a given title needs at its capture rate is UNRESOLVED.
- CONSEQUENCE (recorded honestly): with default game, a client title whose captured motion is actually
  real-time-driven can play FAST (the Issue-2 failure). Whoever cuts a client build MUST re-evaluate the
  correct mode for that title on that box and set `[AnomalyCapture] ContentClockDefault` explicitly before
  shipping — an OPEN item, not settled by m14. Tracked future: owner tests wall vs game on the office
  machine; a per-clock-layer stamp may eventually be needed (out of m14 scope).
- Code change for the flip: the member initializer `EContentClock::Wall → Game` (one line); the
  GConfig-absent fallback already resolves to the member default, so it follows automatically. Everything
  else in m14 is exactly as gated. Re-verified after the flip: a fresh session with NO ini key logs
  "Content clock: game (stamp target fps)" and Status shows clock=game (the inverse of the G5 result run
  under the wall default) — see below.
- **D2 stamp branch (ComputeRunPacing):** wall mode UNCHANGED from m11 (ratio>tol → sustained; within-tol
  → target; faster-than-target → target, one-sided). game mode → `StampedFps = VideoFps` (target) at ANY
  ratio; SustainedWallFps/SpeedRatio still computed + recorded. `WriteSessionAnnotationFile` unchanged —
  it already writes `video.fps = StampedFps` + `target_fps`, so the mode-correct value flows through.
- **D3 warnings per mode:** game mode's early (≥30-arm) and finalize warnings say the video is CORRECT and
  the slowness is a capture-time perf issue ("live capture ran slow … stamped at target F and plays
  natural"); wall mode keeps the m11 "stamped at the true rate X" wording. The pacing summary line gains
  `clock=`.
- **D4 record:** `WriteRunSummary` gains a `content_clock` string → run_summary.json. Kept in run_summary
  only (annotation is the client file; its `video.fps` already encodes the decision).

Files: AnomalyCaptureSubsystem.{h,cpp}, AnomalyLabelWriter.{h,cpp}. IAnomaly/injector/anomalies/control
