## Ambiguities → rulings
- **AMB-M2-1 (A2/GDPCvar + near-clip mechanism) → defer A2.** Source check: `r.SetNearClipPlane` is an
  `FAutoConsoleCommand` over the CORE global `GNearClippingPlane` (synced by RenderCore's
  `SetNearClipPlaneGlobals`), **not** an `IConsoleVariable` — so `FindConsoleVariable→GetString/Set`
  returns null for it. A2's only would-be M2 consumer can't use it → zero real consumers → would violate
  the ≥2-consumers bar. Ruling: defer `GDPCvar` to the post-process/scalability milestone; implement
  `camera_clipping` self-contained (no `RenderCore`; option (c) rejected). M2 ships 2 helpers. Gotcha G13.
- **AMB-M2-2 (static vs skeletal LOD) → static-mesh-only v1.** Different APIs on different base classes
  (`SetForcedLodModel` vs `SetForcedLOD`/`GetForcedLOD`); the deterministic targets are static; the only
  skeletal candidate (the Bot) is runtime-spawned/non-deterministic. Skeletal is an M3 follow-up. G16.
- **AMB-M2-3 (MainWorld targets) →** primary LOD target substring `Boulder` (deterministic; `RockFlats`
  backup); confirm a Movable light live (`Mobility==Movable`, try DirectionalLight first), only add a
  Movable PointLight to a test sublevel if none exists (not preemptively).
- **AMB-M2-4 →** leave M1 anomalies untouched (A3's two consumers are the new anomalies).
- **Minor approved:** GDPArgs as Public h/cpp; lighting `off` = `SetVisibility(false)`.

### Port watch-items (UE 5.4 → 5.1) — pre-brief source skim, **NO changes made**
Candidates to verify against 5.1 source + the 5.1 host when the port brief lands. Most are expected fine;
listed so the port re-gate is fast.
- **C++ standard default.** UE 5.4 defaults to **C++20**, UE 5.1 to **C++17**. The plugin `Build.cs` does
  **not** pin `CppStandard`, so it inherits the engine default. Our code uses only C++11/14 constructs
  (templates, `final`/`override`, `constexpr`, default member initializers, range-for, lambdas) — no
  C++20-only features (no concepts / `<=>` / designated initializers). Expectation: compiles under C++17;
  verify, and consider explicitly pinning `CppStandard` for determinism.
- **`AActor::GetComponents<T>(TArray<T*>&, bool=false)`** (A1, `GDPTargeting.h`). The `TArray<T*>` overload is
  long-standing, but the `GetComponents` overload set (incl. `TObjectPtr<T>` variants) grew over versions —
  confirm the `TArray<T*>` call still resolves unambiguously on 5.1 (expected yes).
- **`USceneComponent::SetVisibility(bool, bool=false)`** (lighting_mismatch). We use the long-standing
  `bool` overload; the `EVisibilityPropagation` overload is newer (5.3+) and we do **not** use it. Confirm the
  `bool` overload is present on 5.1 (expected yes).
- **Near-clip path** (`GNearClippingPlane`, `r.SetNearClipPlane` command, `GEngine->Exec`) and the **light/mesh
  setters** (`SetIntensity`/`SetLightColor`/`SetCastShadows`/`GetLightColor`/`GetVisibleFlag`,
  `SetForcedLodModel`/`ForcedLodModel`, `UStaticMesh::GetNumLODs`) are all 5.0+; expected identical. Confirm
  `r.SetNearClipPlane` is still an `FAutoConsoleCommand` over the same global.
- **Re-gating, not compilation:** target identification will differ on the 5.1 **host project** (a different
  game, not StackOBot) — the movable `DirectionalLight` and the instanced-foliage / single-LOD findings
  (G14/G15) are StackOBot-specific and must be re-discovered. World Partition / OFPA streaming differs 5.1↔5.4,
  affecting which actors are loaded at smoke time.
- **Host scaffolding** (`Source/StackOBot/*`, `*.Target.cs`) lives outside the plugin and will be recreated for
  the 5.1 host; any `CppStandard` / `IncludeOrderVersion` / `DefaultBuildSettings` pins there are host concerns.
