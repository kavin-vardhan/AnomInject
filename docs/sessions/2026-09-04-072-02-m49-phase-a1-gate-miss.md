## §2. `MPP_Outline` — the required read, ANSWERED: **ANY NON-ZERO**

`Content/Effects/Materials/PostProcess/MPP_Outline.uasset` does **not** select by a graph
comparison; it uses the **engine's post-process stencil test**:

- **`bEnableStencilTest` is PRESENT** in the tagged-property name table ⇒ non-default ⇒ **true**.
- **`StencilCompare` and `StencilRefValue` are ABSENT** ⇒ both at engine defaults.
- `StencilRefValue` has the inline default **`0`** (`Material.h:940`).
- `StencilCompare` has **no** inline and **no** constructor initialiser, so it takes the enum's zero
  value, which is **`MSC_Less`** (`EngineTypes.h:774-783` — `MSC_Less` is the first enumerator).
- The engine's own CPU mirror: `case MSC_Less: bStencilTestPassed = (StencilRef < StencilValue)`
  (`PostProcessMaterial.cpp:159`), and the GPU state table maps that slot to `CF_Less`
  (`PostProcessMaterial.cpp:88-104`).

⇒ **the material runs wherever custom stencil > 0.** It selects no particular value.

✅ **The instrument proved itself BOTH WAYS (`G96`)** — the same scan SHOWS `bEnableStencilTest`,
`BlendableLocation`, `MaterialDomain`/`MD_PostProcess`, all non-defaults, so its **silence** on
`StencilCompare`/`StencilRefValue` is a reading and not blindness.

🚨 **CONSEQUENCE: every census-tagged actor (200..254) falls inside `MPP_Outline`'s stencil test in
frames the labels call CLEAN.** The 069 hazard is no longer hypothetical on this host.

## §3. The onset-gap mechanism — MEASURED, and it is an ENGINE ordering property

**`FMulticastDelegateBase::Broadcast` iterates the invocation list in REVERSE registration order**
(`MulticastDelegateBase.h:163`), and the engine states it in its own comment:
`// call bound functions in reverse order, so we ignore any instances that may be added by callees`.

`Initialize` bound `OnWorldTickEndMask` first (`:355`) and `OnWorldTickEndSample` second (`:356`),
so **Sample ran FIRST and Mask ran SECOND**. `SampleDeferredActiveState` fills `MaskValues` by
searching `MaskMeasure.GetRecords()` for `(Id, Target, StartFrame)` and **defaults to `0`** when the
record is absent; the records are created by `EnsureMaskRecordsForCapturedFrame()`, called from the
**Mask** handler. ⇒ on a fire's **first captured frame** the record did not exist yet.

**The confirming reading, taken BEFORE the fix and recorded in the predictions file:** the
`mask_value == 0` entry is each fire's **first fire-active captured frame, and no other entry**:

| session | first-active frames with `mask_value==0` | any other row with 0 |
|---|---|---|
| Lyra `LYRA_SMOKE_01` | **6 of 6** | **0** |
| StackOBot `B20_M45_FULL_NAT` | **6 of 6** | **0** |

🔑 **The 4/4-vs-0/2 class split 072-01 reported is a CONSEQUENCE, not the mechanism.** The gap hits
every fire's first active frame; for `FireWindow` ids that frame *is* the first labelled frame, so
the zero is visible in `annotation.json`; for `ActorHidden` ids the first labelled frame is the first
**hidden** frame, which is later, so the zero lands on an unlabelled row. Journal 071 §11.2 saw one
instance and called it sporadic — **it is systematic, on both hosts, in every session since `m43`.**

**FIXED STRUCTURALLY.** ⛔ Swapping the two `AddUObject` calls was **rejected**: that would rely on
reverse-broadcast continuing to hold, and this project has already ruled (journal 068 §8, the P9
tick-order finding) that **an ordering guarantee cannot be requested, only constructed.** One
`OnWorldTickEnd` handler now calls the mask block and then the sample block in **explicit written
order**; the two bodies are unchanged.

✅ **RESULT — the headline gate, on the same auto-pool recipe as the banked datum (`G184`: payload
taken from `B20_M45_FULL_NAT`'s own `run.json`/`_leg_geometry.json`, not from prose):**

| | first-active frames with `mask_value == 0` |
|---|---|
| `DE65F84A` (pre-fix, banked) | **6 of 6** |
| `1C859DC9` (post-fix, `A1_NAT`) | **0 of 6** |

Every fire's first active frame now carries its own tag (`227/228/229/252/253/254`), and no row

**DIAGNOSED, NOT GUESSED.** `observable = active && ConditionHeld && target_pixels >= min`.
On those frames `target_pixels` reads **48,591** and `frames_condition_lost` is **0**, so neither the
pixel term nor the condition term is false. **The false term is `active`.**

I used `Snap->FireActive`. **`FireActive` is meaningless for `FireWindow` ids.**
`ComputeFireActive`'s fallthrough returns `IsLogicallyHidden(FActor)`, which is **false for a texture
swap** because the actor is not hidden. Journal 071 §3.1 says exactly this — *"`FireWindow` ids fall
into the same else branch but the value is never consulted for them"* — **and I consulted it.**

🔑 **The correct predicate ALREADY EXISTS and is already used elsewhere: `IsFireLabelledThisFrame`,
whose `default:` branch returns `true`.** The fix is to use it as the `active` term.
⚠ **Second consequence of the same mistake:** `FramesConditionLost` is incremented inside
`if (bActive && !bHeld)`, so it can never fire for texture types either. Its `0` this run is
**blindness, not a clean read** — exactly the `G96` shape, in my own counter.
