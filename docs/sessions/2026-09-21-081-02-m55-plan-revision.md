## §3 The seven source facts that decided the design

Every line below was re-read this session on `287ad3e`, whose diff against `031a103` is documentation
only — so these are `master`'s lines.

1. 🚨 **v1's identity pin cannot resolve.** `Async->PendingSnapshots.Remove(Frame.RequestId)` runs
   immediately after the writer job is enqueued (`AnomalyCaptureSubsystem.cpp:4153`). By the time frame
   `N` is processed, `N-1`'s snapshot is already gone. v1 proposed resolving *both* request ids through
   that map. `F2`'s first point, confirmed.
2. 🚨 **Arrival order is inverted, and the inversion is exact rather than hypothetical.**
   `Drain_RenderThread` scans in-flight items **backwards** (`AnomalySveCapturer.cpp:287`) and appends
   ready ones to `Completed` (`:359`); `PopCompleted` pops `Completed[0]` FIFO (`:371-379`). `InFlight`
   is appended in submit order, so **two frames that become ready in one drain pass are popped
   newest-first.** Held batches re-order it again (`AnomalyCaptureSubsystem.cpp:3892-3893`, `:3937-3948`,
   bound `GTargetMaskMaxHoldTicks = 4` at `:169`). ⇒ an ordered CPU stage is a **necessity**, not a
   precaution — this is sharper than Codex's general statement and is the strongest single argument for
   `R3`.
3. 🚨 **Colour and mask consume arms differently.** Colour takes one wanted request per publish, FIFO
   (`AnomalySveCapturer.cpp:45-73`). The mask takes **all** pending arms —
   `ServedIds = MoveTemp(PendingArms); RequestId = ServedIds[0]`
   (`AnomalyMaskSceneViewExtension.cpp:122-131`) — and **clones one render's result to every served id,
   with only one `PixelOwner` receiving `MaskPixels`** (`:512-529`). A session index therefore does not
   name one render for both. ✅ Half of that case is *already* refused today: `ServiceTargetMask` reads
   `MaskPixels.Num() < W*H` and lands `Unmeasured` (`:1279-1290`). ⛔ The other half — a clone that did
   receive pixels but is not that index's render — is closed only by a receipt.
4. 🚨 **The canonical bytes exist in exactly one place, and it is not where v1 put the measurement.**
   `EncodeAndWriteFrame` is `ConvertTightToBGRA(...)` → `ResampleAndEncodeBGRA(...)`
   (`AnomalyLabelWriter.cpp:296-306`, `DecodeTightPixel` `:266-294`). ⇒ measuring the **writer's own
   buffer** makes agreement with the delivered PNG structural. It also resolves `F7`'s counterexample
   outright: a 10-bit red `0 → 35` is `(35 >> 2) = 8` bytes, **not** `8.724`, so a strict `> 8` threshold
   correctly does not count it — the delivered picture and the measurement agree because they are the
   same bytes.
5. 🚨 **`DecodeTightPixel`'s `default:` returns BLACK** (`:291-293`). An unhandled source format would
   therefore read *zero change everywhere* — an instrument reading quiet while blind, `G96`/`G159`'s
   shape. Hence `unsupported_delivery` covers the source format as well as JPEG, resample and multi-view.
6. 🚨 **A per-row change field in `labels.jsonl` is impossible without delaying every row.** The row is
   serialised in the drain (`BuildLabelRecordForSnapshot`, `:4132`) and handed to the writer at `:4151`,
   **before** that frame's canonical buffer exists. ⇒ v1 writes its per-pair numbers to a **new per-run
   sidecar** instead — which simultaneously closes `F3`'s delivery hole, because
   `Job.bWriteLabels = !bDeliveryMode || bLabelsInDelivery` (`:4150`) can switch `labels.jsonl` off
   entirely. The sidecar is written **once at finish, sorted**, not appended per frame, because
   `Async(EAsyncExecution::ThreadPool, ...)` (`AnomalyAsyncWriter.cpp:22`) is unordered and concurrent —
   `G162`'s recorded cause.
7. 🚨 **The producer cannot supply a pre-onset silhouette, for any class.** Target-mask arming is gated on
   `IsFireLabelledThisFrame` (`AnomalyCaptureSubsystem.cpp:1156`, predicate at `:4845-4865`), so the frame
   **before** a phase begins is unlabelled and is never armed. ⇒ `prev_target_pixels` is `-1` on **every**
   onset pair, by construction. It is meaningful only on window pairs 1..3. **`m55` v1 does not establish
   pre-onset visibility**, and the only thing that would is a lookahead the producer does not have.
   Declared as a limitation, not filed as work.

## §6 Three design choices worth defending explicitly

### 6.1 One class, two registered ids

Codex `F4` asks for a null and a positive *through the same path*. The plan implements both as
`FAnomaly_ChangeCase(FName Id, bool bSwapMaterials)`, registered twice. Sharing the class makes the
picker, the fire lifecycle, the labelling source and the arming **identical by construction**; the two
arms differ in exactly one boolean. Two independent classes would differ in more than one variable and
the comparison would be worth less.

Declared scope, because `F4` requires it: both ids are in `ResolveAnomalyActiveSource`'s map as
`FireWindow` so neither rides the unknown-id default (`AnomalyCaptureSubsystem.cpp:281-296`); **neither is
in `GAutoPool` (7), `GAutoPoolDefaultEnabled` (4) or the selector's `GAnomalyChoices` (5)**; `Apply`
refuses by name unless `IAI.Bench.ChangeEvidenceCases 1`; and the **registered catalogue moves 10 → 12**,
which `IAI.ListAnomalies` and the dashboard's authored-spec list will show. That last one is a visible
consequence and is stated rather than discovered.

### 6.2 The gate condition for the twin is an ORDERING, not a threshold

`R8` removed calibration, so no numeric separator is available. The gate is therefore: `solid_swap`'s
onset `chg_gt8/chg_n` is **strictly greater** than its own control and than `null_effect`'s at the same
fixture and pose. An ordering between two arms of one class is `G96`'s "prove it can fire, both ways"
without smuggling a calibrated floor. ⛔ If the ordering fails, that is a finding — the metric is reading
the renderer, not the anomaly — and explicitly **not** a threshold to tune.

### 6.3 The schema gate carries no literal per-event key count

`G-SCHEMA` asserts key **sets** by set difference (added ∅, removed ∅) rather than literals. This project
has shipped a stale literal count in a delivery gate **three times**, each one that *"would have FAILED A
CORRECT BUILD"*. The counts measured mechanically this session — `annotation.json` root **4**,
`run_summary` root **86** — are recorded in the plan as *readings*, not as gate constants.

## §7 Deviations from the brief, flagged rather than bent

**One, and it is a wording deviation with a measured reason.** The brief says `solid_swap` swaps to *"a
flat unlit colour."* The plan uses the already-shipped **Lit** `M_CorruptedTexture_Pink`:

1. `G50`/`m29` measured that an unlit-emissive magenta **lit the Lumen scene and glowed onto
   neighbours** — which on a Lumen host inflates exactly the control this pair exists to read. An unlit
   material in UE outputs through Emissive by construction, so the hazard is structural, not incidental.
2. A new material asset is new plugin `Content`, which forces the full cook §4 above otherwise avoids.

Stated in the plan (§7.2) as a flagged deviation for the reviewer to overrule, not applied silently.

**Nothing in the brief was found impossible by the source.** Two items were found *structurally
constrained* and are declared as such rather than quietly satisfied:

- `R6`'s *"the onset pair's prev-frame `prev_target_pixels` is published as the pre-onset visibility
  record"* — the field is published as instructed, **and its value is `-1` on every onset pair by
  construction** (§3 fact 7). So the field exists and the *record it was meant to carry does not*.
- `R3`'s cut handling — level/world/reset is covered by the epoch; a **same-size camera cut is not
  detectable** by anything in the producer, and is reported only through `cam_moved`, which `R3` itself
  defines as a caveat rather than a validity rule. Carried in the gate table as **UNEXERCISED with its
  reason** and with what would exercise it named.

threshold:

with no expected value. ⛔ Artifact arithmetic only — not certification of pairing, effect or cause.

## §9 What the plan deliberately does not do

- ⛔ It does not change `observable`, and does not propose when to. That is an owner/client decision under
  `docs/OPERATING-CONTRACT.md` §3, and keeping `label_schema` at 2 with unchanged key counts does not
  waive it (`F3`, verbatim).
- ⛔ It does not choose a floor, a control cap or a class threshold. `tau_px = 8` is the *existing*
  verifier threshold adopted so the two instruments measure the same quantity, published per row, with an
  8-bin histogram so any other threshold is recoverable offline without a re-capture.
- ⛔ It does not move `annotation.json`, `labels.jsonl` or `label_schema`.
- ⛔ It does not flip `GAutoPoolDefaultEnabled`, raise `MaxCoAffected`, tune the `m52` ratio, or build S2′.
- ⛔ It does not let `change_*` become an input to the `m26` veto. The 077 ruling removed a veto built on
  `target_drawn_pixels` for exactly this reason; `G258` is the standing warning.
- ⛔ It does not claim causation, persistence or perceptibility. `G263`'s correction is not repealed by
  moving the measurement in-engine.
