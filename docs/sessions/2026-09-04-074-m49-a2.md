### §1.1 The picker exclusion, and the one place it must NOT go

`AnomalyViewport::IsTranslucentOnlyComponent(Comp, bAllowCustomDepthOptIn)` is now shared; the
census dropped its private `ComponentSlotsAllTranslucent` and calls it. An actor is refused iff it
has ≥1 renderable-visible component and **every** one is translucent-only.

🔑 **It is applied in `ClassifyRenderableVisibleLive`, NOT in `IsRenderableComponent`.** The `G33`
chokepoint is where the `m27` foliage exclusion lives and was the obvious place. It is wrong here:
the census calls `IsRenderableComponent` and then applies its OWN translucent rule on top, so an
exclusion at the chokepoint would make translucent components stop counting as `Renderable` at all,
`TranslucentOnly == Renderable` could never hold, and **`census_excluded_translucent` would read a
permanent 0** — a live diagnostic silently retired (`G96`). Declared in the predictions file §1.1
before any leg, not discovered afterwards.

⚠ **The two consumers pass a DIFFERENT ARGUMENT on purpose.** The census passes its configured
`bIncludeTranslucentCustomDepthWriters` (default `false`); the picker passes `true`. The census asks
*"is this in my measurable population under my policy"*; the picker asks *"can the target mask
measure this at all"*, and a translucent material opting in via `IsTranslucencyWritingCustomDepth()`
**can** be measured. The predicate is shared; the argument is not, and that is stated rather than
left to a future diff.

**Cost when ON is bounded:** the full component pass runs only for actors whose FIRST
renderable-visible component is itself translucent-only. Everything else short-circuits on one cheap
material read and traces nothing extra. OFF is byte-identical in result and cost.

### §1.2 `m39` folded in, additive

`FTargetMaskOutcome` gains `Bounds` beside `Counts`; the same drain join that fills `target_pixels`
fills `Snap->DrawnBounds`, **indexed by the same `mask_value` the row emits**. Rows gain
`bbox_drawn_px` (null when there is no drawn box), events gain `bbox_source`.
⛔ **`bbox_px` is NOT replaced.** The honest-bbox milestone's *replacement* of the projected box is
not done and is not proposed here.

### §1.3 `mask_map.json` — the `last_frame` defect, stated

`first_frame`/`last_frame` were keyed on the **stencil VALUE**. Values are reused across events —
the file's own `note` says so and tells the reader to disambiguate *by the frame range*. So two
events sharing a reused value reported **one merged range for both**, breaking exactly the
disambiguation the note asks for. They are now scoped to the EVENT via a per-request
`tag -> event_id` map recorded at arm time.
⚠ **The fix is INERT on this fixture** — no G-EDGE or auto-pool leg this session reused a value
within one run (`reused values sharing an IDENTICAL range: 0` on every leg). Its correctness rests
on the code path, not on a leg that exercised it. **Said, not glossed.**
