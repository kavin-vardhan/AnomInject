## 3. G-MODE: two family mix-ups, fixed and re-evaluated offline
### 3.1 The two mix-ups
1. **The gate (`089-04-oracle.py` `judge_session`):** every family's rows were gated on the overall `porc["pass"]`, which
   needs uv16, uv64 **and** n to pass on the null's frames. The uv MODE legs use MODE_UVNULL, whose frames are lit (the uv
   recipe leaves `ShowFlag.Lighting` at its default 2), so the n reading fails there and the uv rows read INSUFFICIENT
   `porc_failed` although both uv oracles pass. The normal MODE legs use MODE_NNULL (`ShowFlag.Lighting 0`, read back),
   where all three readings pass, so they read PASS. **The as-built normal PASS was correct; the as-built uv INSUFFICIENT
   was the error.**
2. **The premise lock (`089-04-window.py:175`):** `lk['p_orc']=ORC.p_orc(fr(u)+fr(nn))` pooled three P_ORC_UV frames and
   three P_ORC_N frames and ran all three oracles on all six. The n oracle read the three lit uv-recipe frames and failed
   (§6), so the lock recorded P-ORC FAIL with the normal oracle failing. Re-running the same call offline reproduces the lock
   exactly (`porc-split.json`, `pooled_reproduces_lock: true`).

The ruling read these together as "normal reads PASS although normal's P-ORC failed". Both halves come from the same
mix-up: the "normal P-ORC failure" is the n oracle judging frames rendered for the uv family.

### 3.2 The fix (declared; `_reviews\089-04b-evidence\gmode-fix.diff`)
- `judge_session_family` = the frozen `judge_session` with one change: each family's rows are gated on **that family's**
  P-ORC — uv rows on uv16 **and** uv64 (median and every per-frame reading), normal rows on n — with the reason
  `porc_failed:<kinds>`. It drops the `null_as_modes` block, which G-MODE never read (its NULL_AS_MODES rows come from
  `089-04-eval.py` `null_modes`); the re-evaluated NULL_AS_MODES equal the as-built ones.
- Declared, not applied: the premise lock computed per family on its own recipe (uv16 / uv64 on P_ORC_UV, n on P_ORC_N).
- **Unit tests 12/12** (`gmode-selftest.json`), both directions on the real banked legs: the frozen gate reproduces the
  defect on MODE_TILE; a uv row is not INSUFFICIENT when only the n reading fails; a normal row judged on a null whose n
  reading fails (MODE_UVNULL) does **not** pass (INSUFFICIENT `porc_failed:n`); doctoring n to fail on MODE_NNULL stops the
  normal row passing; doctoring uv64 stops the uv row passing; doctoring n does not move a uv verdict; on a null where all
  readings pass, the frozen and family gates agree; the pooled lock reproduces the as-built FAIL; per family on its own
  recipe each passes and n on the lit uv frames fails.

## 4. RD5 "end −4" — an evaluator reference defect, not a label defect
- **The lever and the log (event start 58):** `IAI.Bench.TexCorruptRestoreDelay 5 - REVERT called at frame 68 … until
  frame 73`, then `delayed restore runs now (due) at frame 73` and `REVERT restored-exact=1 … restore_delay=5`. RD3: 68 → 71.
- **The capture skips two engine frames after each transition** (gfc 59–60 after the fire at 58, 69–70 after the revert at
  68). So the 5 still-corrupted engine frames 68–72 are captured as **3** frames (gfc 68, 71, 72 = si 55–57), and RD3's
  68–70 as 1 (si 55). That is why 089-01 ruling 4 declared RD5 +3 and RD3 +1 in captured frames.
- **The pixels (`089-04b-rd5.py`, mean |Δ| in the event's 4,096-px mask ROI against the clean pre-reference si 44–46, noise
  0.35):** labelled si 47–54 read 73.10–73.12; unlabelled si 55–57 read 73.10–73.11; si 58 (gfc 73) reads 0.35 and si
  59–66 ≤ 0.59. **Every labelled frame is fully corrupted; the picture outlasts the label by exactly 3 captured frames.**
  t50 end offset **+3 on 8/8 events** on both RD5 legs (the AA-on threshold count reads 3–5 on the TSR tail; t50 reads 3);
  RD3 +1 on 8/8; CD5 start +3 on 8/8; the fixture control F_TILE_NAT t50 0 on 9/9.
- **Why E1 reads −4:** E1's offset reference for each run is the six frames after the last label (si 55–60). On every
  judged RD5 event three of them (55–57) are still corrupted. The office-kit trim (`089-03-eval.py:1125-1145`) tests each
  leading frame against the median of the rest with a noise threshold taken from that same rest, and it dropped nothing
  (recorded `settled: true`, `dropped_leading: []`), leaving a half-corrupted reference and `thrD_off` 59.1 (RD3: the trim
  drops si 55, `thrD_off` 1.57, and E1 reads +1 correctly). Against that reference E1 records the off half of the labelled
  run, si 51–54, as `labelled_not_visible`, hence end −4 on 7/7 (AA-off) and 6/6 (AA-on) judged events.
- **Verdict:** not the lever's semantics (it does what it declares), not the settle skip (it is what turns 5 into 3), and
  **not a label defect** — no labelled frame is clean. It is the frozen E1's offset reference, which cannot hold a window
  that is half late picture. E1 still FAILs the leg (the can-fail direction holds) but names an over-label of 4 where the
  truth is an under-label of 3. The kit reads NO-JUDGED-EVENT there (the safe direction).
- **What would fix it next time (declared, not applied — E1 is frozen):** take the offset reference from frames proven
  settled against the onset reference's noise (on a static fixture the pre-event clean image is the post-event clean
  image), or start it beyond the largest lag the leg can have; read any arm that pushes the picture past half the window
  in pixels as well. → G419.

## 6. The normal P-ORC "failure"
The normal oracle does not fail with `ShowFlag.Lighting 0`. On P_ORC_N's own frames (Tonemapper 0, Lighting 0, both read
back) it reads 16 cells, separation 45, interior spread 0, residual 1.1e-10 px, pattern worst-same 0 / worst-diff 45: PASS
on each of the three frames, and 8 of 8 on MODE_NNULL. It fails only on the three P_ORC_UV frames, which the uv recipe
renders lit (`ShowFlag.Lighting 2`, the default): interior 12, residual 0.65 px, pattern worst-same 21 — the normal-map
tile shaded by the scene light. The as-built premise lock pooled both recipes' frames and took the median (interior 6,
pattern 10), so it recorded a FAIL. **Next time:** compute the premise P-ORC per family on that family's own recipe and
gate each family's G-MODE rows on it (§3.2). No oracle, fixture or show-flag change is needed for normal. → G420.
